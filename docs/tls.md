# TLS and private certificate authorities

Yes: cert-manager can issue private certificates for Service DNS names, and Arkime's database clients can trust a private CA. A public certificate is not required. The [getting-started walkthrough](getting-started.md) includes a namespaced CA issuer, OpenSearch node/admin certificates, CA trust for Arkime, and a certificate for a Traefik HTTPS listener.

However, the current operator does **not** provide TLS for every Arkime-to-Arkime connection. Issuing certificates does not automatically mount them, enable HTTPS listeners, or switch clients to HTTPS.

## What is encrypted today?

| Connection | Current operator behavior | Certificate/trust configuration |
| --- | --- | --- |
| Capture, viewers, bootstrap/retention Jobs → database | HTTPS supported with certificate verification | `database.endpoints` uses `https://`; `database.tls.caSecretRef` supplies the CA chain |
| Separate users/Cont3xt databases | HTTPS and separate CA references supported | `database.users.tls.caSecretRef`, `cont3xt.database.tls.caSecretRef` |
| OpenSearch node → OpenSearch node | Configured by the OpenSearch operator | Walkthrough supplies cert-manager certificates for transport |
| Browser → Traefik/Gateway | HTTPS supported | Gateway listener `certificateRefs` points to a cert-manager TLS Secret |
| Gateway → viewer or Cont3xt | HTTP in the generated configuration | No managed backend HTTPS or BackendTLSPolicy configuration |
| Central viewer → capture-local viewers | HTTP in the default managed setup | No managed serving certificate, HTTPS discovery, or node-IP certificate lifecycle |
| Capture/viewer → WISE; internal Cont3xt URLs | HTTP URLs generated by the operator | No managed component TLS configuration |
| Sender → TZSP receiver (direct or through Traefik) | UDP without encryption/authentication | TLS certificates do not secure TZSP; use a trusted network or an encrypted tunnel |

`web.tlsSecret` configures TLS termination on an **Ingress**. With `web.mode: Gateway`, configure the certificate on the referenced Gateway. Neither setting turns on TLS inside the Arkime pods.

The relevant implementation is `internal/config/config.go` (`ServiceURL`, `Render`) and `internal/resources/resources.go` (`pod`, `container`, `HTTPRoute`). The generated internal Service URLs use `http://`, and the operator has no dedicated API for mounting serving certificates into components. Setting arbitrary Arkime INI keys is not a complete supported TLS solution: it also needs private-key mounts, compatible probes, client trust, and correct discovery URLs.

## Database CA trust

Create a Secret in the **same namespace as the ArkimeCluster**, containing only public CA certificates:

```yaml
spec:
  database:
    engine: OpenSearch
    endpoints: [https://opensearch.arkime.svc:9200]
    auth:
      basicAuthSecretRef: {name: arkime-database, key: basicAuth}
    tls:
      caSecretRef: {name: arkime-database-ca, key: ca.crt}
```

This is a spec fragment, not a complete resource. Keep your existing capture/retention settings. Include the root and any needed intermediate CA certificates in PEM form. The endpoint's hostname must match a SAN in the server certificate; trusting a CA does not bypass hostname verification.

The operator combines configured database CA references into a mounted bundle. Capture uses `caTrustFile`; Node processes receive `NODE_EXTRA_CA_CERTS`; Perl database tooling receives `PERL_LWP_SSL_CA_FILE`. Bootstrap and retention Jobs receive the trust configuration too. Do not set `insecure` or disable verification.

Keep the CA signing Secret separate from this trust-only Secret. Do not copy the CA private key into application namespaces merely to distribute trust. For many namespaces, [trust-manager](https://cert-manager.io/docs/trust/trust-manager/) can distribute a public bundle. This operator expects a **SecretKeySelector**, so configure Secret targets (and the required trust-manager permissions), or maintain a Secret through your existing secret distribution system; a ConfigMap target alone does not satisfy `caSecretRef`.

## Optional database mutual TLS

Server-authenticated HTTPS plus basic authentication encrypts the connection and authenticates the user. Database mTLS additionally presents a client certificate:

```yaml
spec:
  database:
    tls:
      caSecretRef: {name: arkime-database-ca, key: ca.crt}
      clientCertificateSecret: arkime-db-client
  cont3xt:
    enabled: false
```

Have cert-manager issue `arkime-db-client` with the `client auth` usage and `tls.crt`/unencrypted `tls.key` keys, signed by a CA trusted by the database. Configure the database to accept that certificate and map its identity/permissions as needed. The API still requires a database authentication choice; a client certificate does not automatically create an OpenSearch role mapping or replace the configured basic/API-key credentials.

The current pinned Arkime image's Cont3xt integration does not support database mTLS, so the operator rejects this configuration while Cont3xt is enabled. Different client certificates for different database backends are also rejected. Do not use the OpenSearch operator's administrative certificate as an Arkime runtime client certificate.

## Renewal and CA rotation

[Cert-manager CA issuers](https://cert-manager.io/docs/configuration/ca/) issue and renew leaf certificates, but CA lifecycle and distribution remain your responsibility. The walkthrough bootstraps a private root using a [SelfSigned issuer](https://cert-manager.io/docs/configuration/selfsigned/) and exports its public certificate into a separate trust Secret. That export is a point-in-time copy, not automatic synchronization.

- The Arkime operator hashes referenced Secrets and reconciles roughly every 30 seconds. CA/client-certificate updates cause application pods to roll and rebuild their trust bundles. Finite completed Jobs do not rerun simply because certificates changed; new Jobs use current Secret contents.
- Cert-manager updating a Secret does not prove OpenSearch reloaded the certificate. The pinned OpenSearch operator 2.8.0 recipe uses supplied certificates: plan and verify a rolling restart/reload before leaf expiry. Restart one database pod at a time and wait for it to rejoin and cluster health to recover before moving to the next. Check the served certificate after renewal. Do not assume newer operator hot-reload features exist in this pinned version.
- Traefik watches the serving Secret; verify that a new HTTPS connection sees the renewed certificate. Workstation/browser trust stores are managed separately.
- For a CA change, distribute old **and** new trust first, issue and deploy new leaf certificates, verify every consumer, and only then remove the old CA. Update `arkime-database-ca` as well as OpenSearch trust and browser trust. Do not simply replace the root Secret and expect all connections to continue working.

For a long-lived deployment, an organizational PKI or a managed intermediate CA can replace the walkthrough root while keeping the same Secret references.

## What is needed for TLS between all Arkime components?

This requires an operator feature, beyond a documentation or certificate-manager setting:

1. API fields for serving-certificate Secrets and shared trust, with cert-manager Certificate creation either managed by the operator or supplied by the user.
2. Private-key mounts and HTTPS listener settings for central/local viewers, WISE, and Cont3xt, plus HTTPS-compatible probes and certificate renewal rollouts.
3. HTTPS service URLs and authenticated viewer-to-viewer discovery. Node capture currently advertises host IPs, so local-viewer certificates need the actual node IP SANs or a new stable DNS addressing scheme.
4. Gateway backend TLS with verified server identity and CA trust, rather than only edge termination.
5. Integration tests that retrieve PCAP through verified TLS and exercise certificate renewal, wrong-CA rejection, and hostname mismatches.

If encrypting every internal hop is a requirement, the current operator cannot yet meet it with supported configuration. A service mesh or encrypted CNI may provide transport protection, but host-network sensors and UDP require specific coverage checks; neither should be assumed to solve those paths automatically.
